## 1. 目标与成功条件

v1.2 只解决：用户保存的讨论具有正确身份，内容能完整回看，更新不会覆盖用户手动修改。

目标流程：

```text
PDF 选区 → 多轮讨论 → 首次保存 → 继续讨论 → 安全更新
                            ↓
                    重启后完整回看历史
```

成功不以「想明白了」条目数量衡量。继续使用既有五项回忆测试，重点改善第 2、3 项，不宣称本版本已经提供理解演化记录：

1. 最后想明白了什么？
2. 哪个问题最重要？
3. 追问之间是什么关系？
4. 理解发生了什么变化？
5. 还有什么没解决？

## 2. 依据及与旧设计的关系

依据优先级遵循 [决策记录 D-020](Backleaf-决策记录.md)：决策记录 > 当前阶段已冻结设计 > [产品路线](product-roadmap.md) > 历史文档。本文已获确认，适用边界由 D-035 明确。

本方案落实 D-001、D-008、D-013、D-023 至 D-026、D-029 至 D-034 的相关边界：

- AI 的结论不自动成为用户理解；保存对话不得覆盖已确认的 Understanding。
- LiveConversation 与 SavedDiscussion 分离；历史记录可跨 Session 查看，但不复活旧 Session。
- 现代讨论按唯一稳定 ID 定位；legacy 正常读取，不隐式升级。
- Reading Note 是唯一持久化真源，不增加 Conversation 数据库。

[2d.2 历史设计](design-freeze-2d2.md) 曾要求保留全部旧去重规则、不修改 SaveService、两条路径完全 parity。v1.2 提议仅对 Native 现代讨论引入身份驱动保存；legacy/OpenCode 保留旧行为。这是明确的阶段变化，不能假装仍然全路径行为一致。

决策记录 D-035 明确现代与兼容路径的区别，并说明历史约束的适用范围。D-028 的历史管理、D-032 的显式升级仍有效，但实现排在后续版本；本阶段不新增这些入口。

## 3. 范围与不做清单

### 3.1 本版本范围

1. 历史详情逐轮显示全部问题和回答。
2. Native 新讨论采用独立身份，后续保存按 ID 更新同一讨论。
3. 更新前执行基线冲突检测；失败清楚反馈，不覆盖、不另存绕过。
4. 共享最小 Schema 标记定义，补齐正文结构保护与往返验证。
5. 保留既有 Understanding、legacy 读取、原文跳转与当前讨论返回行为。
6. 配套整理当前能力说明、关键状态文案及发布版本一致性；仅描述本版本实际验收能力。

### 3.2 不在本版本范围

- 历史讨论改标题、编辑理解、删除，以及 legacy 显式升级 UI。
- 自动合并、强制覆盖、冲突对比编辑器、理解版本历史。
- 未保存 conversation 跨 Session 恢复、退出拦截、自动保存。
- 流式输出、多 Provider / Ollama、扩展 PDF 上下文。
- 书级导航重做、跨书关联、Recall、全库搜索、阅读计划。
- 大规模重构、换 UI 框架、改存储格式、批量修复旧笔记。
- 自动生成思考树存档、双向同步、删除 OpenCode 路径。
- 本轮部署、提交、打标签或发布；后续按明确的验收和授权边界执行。

上轮审查已用纯内存样例复现误去重和「我的理解」截断；本轮重新核对相关源码。原始 Markdown 仍可能保留被截断的文字，不能把解析缺失表述为已经删除原始文件内容。

## 5. 推荐决策一：身份驱动保存，隔离旧去重

### 5.1 身份与入口

区分以下概念，不能仅凭「输入有没有 ID」推断调用者意图：

- 新 Native LiveConversation：尚无成功持久化身份。
- 已保存 Native LiveConversation：持有 notePath、persistedDiscussionId 和成功保存后的基线块。
- legacy/兼容保存入口：已有 OpenCode 等旧调用契约。
- SavedDiscussion：从 Markdown 读取的历史对象，v1.2 仅查看。

推荐在 SaveService/Writer 边界提供显式的现代创建与更新语义；具体方法名由实现确定。缺少现代身份不得自动落回 legacy 保存。

| 操作 | 推荐行为 |
|---|---|
| 新 Native conversation 首次保存 | 生成独立 `bl_<UUIDv4>`，创建一个讨论块；不以任何现有块的标题/原文阻止创建 |
| 同原文、同标题，但不同 conversation | 创建不同 ID；即使问答内容相同也不自动合并 |
| 同 conversation 后续保存 | 只使用已持有的 notePath + ID 更新；不生成新 ID |
| 无变化再次保存 | 返回成功/已保存语义，不改文件、不新增块 |
| modern ID 0 个或多个匹配 | 明确错误，文件不变；不回退标题、行号、文本或旧全文定位 |
| legacy/OpenCode 保存 | 保留原契约与旧去重；不承诺采用现代 Native 的独立讨论语义 |
| legacy 历史读取 | 正常展示，ID 为 null，不写回、不自动补 ID |

新 Native 创建必须绕过整条旧内容判重，不能仅从候选中排除带 ID 的块，否则相似 legacy 块仍会挡住新讨论。

### 5.2 重入与失败

- 同一 conversation 正在保存时禁用/拒绝重复提交；创建和更新沿用共享写入队列。
- 一次创建操作在写入前生成并保留候选 ID，明确失败重试不另造身份；只有确认成功后才登记为 persistedDiscussionId。
- 创建时若最新文件已有相同候选 ID：唯一匹配且内容等于本次拟写块，可按幂等成功处理；内容不同或多个匹配则拒绝。
- 保存结果返回实际持久化 ID 和实际目标块基线；不得把「准备生成的 ID」当作未确认写入的成功结果。
- 无效/缺失 ID 的更新请求拒绝。历史无 ID 数据继续可读，升级另行实施。
- 当前 Session 的实时理解保存也要采用同一身份和冲突契约；这不新增历史编辑能力。

### 5.3 兼容测试边界

旧入口的 parity 测试继续保护旧行为。现代创建/更新单独测试身份语义；不得为了让全路径 parity 继续通过而恢复误去重，也不得批量修改旧期望掩盖变化。两条路径仍共享可读取的 Reading Note 格式，但不再要求去重结果完全一致。

## 6. 推荐决策二：唯一 ID 定位 + 完整基线比较

### 6.1 基线定义

采用上次成功写入后实际持久化的目标讨论块文本作为基线，保存在当前 Session 内存中。基线包含 heading、discussion marker、正文、来源与 Understanding；不包含下一章节/讨论及块间分隔空行。

统一块边界提取规则。比较允许 CRLF/LF 等价，其他块内字符、空白与格式变化均视为外部编辑。不要通过重新序列化最新解析结果来抹掉用户修改，也不新增哈希或持久化 revision 元数据。

ID 回答「改哪一条」；基线回答「这条是否仍是我上次确认的内容」。旧全文不再用于定位现代讨论。

### 6.2 权威更新过程

在同一个 `Vault.process()` 回调的最新内容中执行：

1. 校验路径范围及目标文件。
2. 解析并确认该 discussionId exactly one match；marker 无效、重复或存在歧义则拒绝。
3. 提取该块，与当前保存基线比较。
4. 不一致则返回原文件内容，报告冲突。
5. 一致则构造目标块，保留 ID；更新对话时保留已保存 Understanding。
6. 仅替换目标块，保留其他块、章节、用户内容和无关格式。
7. 无变化不写文件；成功后更新内存基线，再更新 UI 保存状态。

预读只能用于预检查，不能替代回调内的权威检查。会话队列不能保证另一 OpenCode 进程也受它控制；不宣称本版本解决了所有跨进程并发写入。

### 6.3 冲突呈现

推荐文案：

> 这条讨论在笔记中已被修改，本次更新没有写入。请打开读书笔记核对；当前对话仍保留在本次会话中。

分别反馈：目标缺失、ID 重复/异常、内容冲突、写入失败。错误不得显示成「已保存」或「已有相同讨论」。保留可查看的详细原因，但不要求用户理解内部 ID。

v1.2 只提供查看笔记和保留当前草稿；不提供强制覆盖、自动合并、自动改基线重试或自动另存。冲突后的下一次更新仍须通过同样检查。

## 7. 推荐决策三：历史详情忠实恢复逐轮问答

- 沿用 Native Chat 的角色标签、Markdown 渲染与阅读排版，不改成 Thought Tree 嵌套布局。
- Schema v1 的 firstQuestion 显示一次，随后严格按解析后的 dialogue 顺序显示每轮消息。AI 标记的 ai/assistant 在读模型边界统一；不在 view 中猜测结构。
- 不把所有 AI 回答 join 成一个消息；不按文本相等删除重复问题，用户可能确实重复问过。
- 如兼容输入本身含首问，依据该输入格式的明确映射去重，不能用正文相似度猜测。
- 原文、来源、Understanding 分别展示；Understanding 不混入 AI 对话，保留 source/status 语义。
- resolved 文案统一为「想明白了」，unresolved 为「还没想透」，缺少结构化理解为「未总结」；不把来源确认与理解状态混为一谈。
- 历史详情仍只读；入口文案为「基于此原文开始新讨论」，明确创建新 conversation，不携带旧问答冒充原 Session。
- 「返回当前讨论」保留现有快照恢复与上下文一致性；历史查看不得改动当前对话或待保存内容。
- 保留嵌入保护、代码块、列表、引用和 Markdown 相对链接的来源路径语义。

## 8. 推荐决策四：共享最小 Schema 标记，验证正文边界

推荐新增一个无 Obsidian、DOM、网络依赖的小模块，集中定义字段和机器标记，例如 `src/core/reading-note-schema.js`（路径为建议，不在本轮创建）。Parser、序列化保护和需要这些常量的 Writer 引用它；Writer 不反向依赖 Thought Tree 实现。

字段表包含已有原文、问题、对话、旧版理解、关键点、来源，以及「我的理解」「我的想法」。共享定义不代表新增或改变持久化字段语义。

保护与解析契约：

- 正文中出现结构字段、speaker 标记和 `#` 至 `###` 标题，不得产生新讨论、伪造角色或切断消息。
- AI/用户正文中的 `backleaf:discussion`、`backleaf:understanding` 示例也不得被当作真实元数据，尤其不能成为已确认的 Understanding。
- 检查首问、追问、AI 回答、原文引用和理解正文等文本输入边界；不能只保护 AI 答案。
- 对代码块中的同名标记作显式处理，保留内容可读性。当前格式已有保护性转义，往返验收比较可读正文与角色顺序，不要求转义后的 Markdown 字节等于原始输入。
- 新写入必须满足完整往返；旧数据继续兼容读取。旧笔记若已含歧义结构，不能推断不存在的边界、自动修复或静默改写。
- view 不再维护独立的字段截断正则。仅在 core 的兼容样例通过后删除对应补偿逻辑；保留必要的展示格式处理。

不在此阶段整体换 Markdown AST 或重写所有历史解析器。OpenCode 兼容产物不顺手重构；新增测试应明确保护现代路径与旧路径各自的契约。

## 10. 渐进实施顺序与停止条件

1. 同步决策记录中的现代/legacy 边界与历史规则适用范围。
2. 建立失败样例，补齐共享标记及往返保护，验证旧数据读取。
3. 完成现代创建、ID 更新、基线冲突检查与既有理解保存接线，验证旧入口兼容。
4. 完成历史逐轮展示和关键状态文案；执行返回当前讨论、来源跳转回归。
5. 整理当前版本说明；版本文件、发布标签与最终构建对应关系在发布步骤统一，不能提前宣称已发布 v1.2。
6. 完整自动化检查和 Clean Test 人工验收；每个切片按既有流程验收后再进入下一步。

如发现必须迁移历史笔记、增加新持久化字段、改变 OpenCode 写入语义或突破本文件不做清单，先更新设计并取得对应范围确认，不在实现中隐式扩张。

## 11. 已确认的设计摘要

用户已整体确认以下四项：

1. Native 现代讨论采用身份驱动保存；新讨论退出旧内容判重，旧入口继续兼容。
2. ID 唯一定位后比对完整基线，冲突只拒绝并提示，不强制覆盖。
3. 历史详情采用 Native Chat 风格逐轮展示，保持历史只读和新旧 Session 分离。
4. 共享最小 Schema 标记并补足往返保护，不进行全面解析器重构或历史数据迁移。
